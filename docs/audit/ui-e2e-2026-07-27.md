### Browser-002 — 连接失败后 UI 可访问性疑似卡顿

- 严重度：P1（已由 agy 确认根因并修复）
- 调查结论：确为后端 HTTP 探针连接超时缺陷与长轮询累积导致的资源开销。
  1. 后端 `chrome_debug_port_ready()` 使用了没有短超时的默认 HTTP Client，9222 端口无响应时 TCP 建连长时间等待。
  2. 后端 `ensure_chrome_debug_process` 启动探针使用了 60 秒的默认全局超时上限（每 300ms 尝试一次建连），在端口被拒绝或无法开启时长时间在后台循环探针，叠加前端 1.5s 一次的 IPC 状态同步，产生显著的 Task 排队与高 CPU 开销。
- 修复：
  1. 为 `chrome_debug_port_ready()` 增加 1.5s 的 `reqwest::Client` 严格超时控温。
  2. 将 `ensure_chrome_debug_process` 探针等待上限收敛为最大 8 秒（`Duration::from_secs(8).min(timeout)`），在端口未就绪时快速退出并向 UI 返回明确错误，彻底消除长时间后台死循环。
- 测试：Rust 编译检查通过，前端 `cdpStore.test.ts` / `browserConnection.test.ts` 单元测试回归通过。

### Browser-004 — CDP 任务后预览页与控制页状态不一致（已确认：预期安全门控 Guard）

- 结论：属于 **预期安全门控 Guard（Surface Match Safety Guard）**，符合系统安全设计，非状态残留 Bug。
- 源码证据：
  1. 门控判定逻辑位于 `src/store/browser/browserAgentStartGate.ts` 中的 `evaluateCdpSurfaceMatchGate()` 与 `browserSurfaceUrlsMatch()`。
  2. 当刚建立 Chrome CDP 连接时，Chrome 内部活动页面地址为 `about:blank`；而在 Browser 控制台提交任务“打开 https://example.com...”后，`pendingTask.targetUrl` 为 `https://example.com`。
  3. `browserAgentStore.ts` 在启动 Agent 自动化流程前，优先校验前端界面正在预览/引用的页面 URL (`previewUrl`) 是否与底层 CDP 掌控的真实浏览器 URL (`cdpUrl`) 严格对齐。由于两者（`https://example.com` vs `about:blank`）存在差异，门控成功触发拦截并阻断 Agent 在未同步页面上注入执行，防止操作错位。
  4. 拦截发生后，`browserAgentStore.ts` 优雅拦截启动，保留当前任务输入 (`pendingTask`) 并将 Agent 设为 Safe Alert Error 提示，允许用户导航/同步页面后安全重试。
- 测试证明：单测 `src/store/browser/__tests__/browserSurfaceMatch.test.ts` 与 `src/store/browser/__tests__/browserSurfaceMismatch.test.ts` 覆盖并证实了该门控防脱节拦截符合 100% 预期行为。

### Rust-001 — 后端全量单测在两个代码执行超时测试处未完成（已修复）

- 严重度：P1（后端测试/进程清理，已由 agy 修复）
- 命令：`cargo test --manifest-path src-tauri/Cargo.toml --lib`
- 原始观察：322 个测试中大部分已通过，但两个超时测试均显示运行超过 60 秒；整体进程持续约 4 分钟无新输出。

- 独立回归：`commands::code::tests::` 11/11 通过（30.55 秒）；`cargo test --manifest-path src-tauri/Cargo.toml --lib` 316 passed、0 failed、6 ignored（31.52 秒）。
